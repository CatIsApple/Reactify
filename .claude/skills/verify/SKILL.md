# 테스트 검증 워크플로

인자로 **저장소 루트 기준 개인 폴더를 포함한 모듈 경로**를 받는다 (예: `/verify CatIsApple/src/diff`).
대상 폴더는 `CatIsApple`, `member-02`, `member-03` 중 하나다. 김다온의 개인 브랜치는 `CatIsApple`, 커밋 scope는 `member-01`이다. 인자나 이미 확정된 사용자 요청에서 개인을 알 수 없으면 먼저 묻는다. `git status`, 현재 브랜치, 다른 팀원의 변경만으로 대상을 추측하지 않는다. 대상이 확정된 뒤에만 해당 폴더의 변경을 참고한다.

이 공용 파일은 세 사람의 독립적인 전체 구현에 같은 검증 절차를 제공한다. 아래 체크리스트는 **Phase 1 중심**이며, Phase 2 테스트 기준이나 테스트 케이스가 이미 제공된 것은 아니다. Phase 2에서는 루트 컴포넌트만 State·Hook을 사용하고 자식은 props만 사용하는 과제 제약을 기준으로 별도 테스트를 작성한다. Fiber는 선택 확장이다.

## 원칙

- **기준은 과제 요구사항이다. 구현 코드가 아니다.** 지금 출력에 맞춰 기대값을 정하지 않는다.
- 구현 방식은 사람마다 다르다. 테스트는 **공개 함수의 입력과 관찰 가능한 결과**(반환값, DOM)로만 검사한다. 내부 함수, private 상태, 함수 호출 순서는 검사하지 않는다.
- 데이터 모양(VNode 구조, patch 형식 등)은 구현을 읽고 그대로 따른다. 다른 모양을 강요하지 않는다.
- 사람이 "테스트만"이라고 하면 구현 코드는 고치지 않는다.
- 파일 읽기·쓰기, 구현 수정과 테스트 실행은 명시한 개인 폴더 안에서 수행한다. 다른 팀원의 코드·테스트·package와 공용 파일을 임의로 변경하지 않는다.
- 구현이 없으면 확인할 수 없는 범위로 보고한다. 통과 수치를 만들기 위해 더미 테스트를 추가하지 않는다.
- 현재 `CatIsApple/`는 사용자 요청으로 코어만 유지하며 테스트·하네스·데모가 없다. 별도 작성·복원 요청이 없으면 아래 테스트 작성·실행 단계는 적용하지 않고, 현재 상태와 확인하지 못한 범위를 보고한다.

## 1. 파악

1. 대상 모듈의 export와 사용 예를 읽는다.
2. 다음을 짧게 정리해 사람에게 보여 준다.
   - 공개 함수와 시그니처
   - 데이터 모양 (예: VNode가 어떻게 생겼는지)
   - 아래 체크리스트 중 이 모듈에 해당하는 항목 번호
3. 구현에 다른 모듈이 필요한데 아직 없으면, 그 항목은 건너뛰고 보고에 적는다.

## 2. 테스트 작성

- 위치: `<대상 개인>/tests/<모듈이름>.test.js` (시작 하네스 예: `member-02/tests/diff.test.js`). 이미 있으면 덧붙인다.
- 도구: `node:test`, `node:assert/strict`. 해당 개인의 `tests/setup.js`가 DOM 전역(`document` 등)을 만든다.
- 검증 도구도 같은 개인의 `tests/helpers.js`에서 가져온다. `member-02/tests/diff.test.js`에서는 `import { canonical } from './helpers.js'`처럼 쓴다. 중첩된 테스트 파일은 그 파일 기준 상대 경로를 사용한다. 다른 개인의 helper를 가져오지 않는다.
- 체크리스트 항목 하나에 테스트 하나 이상. 테스트 이름에 항목 번호와 확인 내용을 한국어로 적는다.
  예: `test('D3 태그가 바뀌면 통째로 교체한다', …)`
- 비슷한 케이스는 `cases` 배열 + `for` 루프로 묶는다.

## 3. 실행

아래는 시작 하네스를 유지한 `member-02` 대상으로, 저장소 루트에서 시작하는 예시다. 경로는 확인한 개인 폴더로 바꾼다. 현재 하네스가 없는 `CatIsApple/`에는 적용하지 않는다. Node.js 22 이상과 해당 개인 폴더의 의존성이 필요하며 최초 설치는 `npm --prefix member-02 ci`다.

```bash
npm --prefix member-02 test                 # 해당 개인의 테스트 전체
```

파일 하나를 실행할 때는 해당 개인 폴더로 이동한다.

```bash
cd member-02
node --test --import ./tests/setup.js tests/diff.test.js
```

저장소 루트에는 package나 테스트 코드가 없으므로 루트에서 바로 `npm test`를 실행하지 않는다. 아직 `*.test.js`가 없으면 테스트 케이스 미작성 상태로 보고하며, 실행 종료 코드만으로 구현 검증 통과를 선언하지 않는다.

## 4. 실패 분류 → 수정 → 재실행

실패마다 원인을 하나로 분류한다.

| 원인 | 조치 |
|---|---|
| 테스트 오류 (요구사항을 잘못 옮김, 셋업 문제) | 테스트를 고친다 |
| 구현 버그 | 구현을 최소 범위로 고친다 |
| 요구사항이 모호함 | 멈추고, 선택지를 붙여 사람에게 묻는다 |

- 고치고 다시 실행한다. **최대 3회.** 그래도 실패가 남으면 멈추고 보고한다.
- 금지:
  - 기대값을 현재 출력에 맞춰 바꾸기
  - 테스트를 `skip`/`todo`로 돌리거나 지우기
  - 특정 테스트 입력에만 맞는 분기를 구현에 넣기

## 5. 보고

다음 형식으로 끝낸다.

테스트·하네스가 없으면 결과는 "테스트 환경 미제공 — 실행하지 않음"으로 적으며 통과 수치를 만들지 않는다.

```
## 검증 결과: <개인 폴더>/<모듈>
- 결과: N개 중 N개 통과
- 확인한 항목: V1, V2, D1 …
- 확인 못 한 항목: (항목 — 이유)
- 고친 것: (테스트|구현) 파일 — 한 줄 이유
- 핵심 로직 (5줄 이내): 사람이 발표에서 설명할 수 있게
```

## 체크리스트 — Phase 1

### Virtual DOM 변환
- **V1** 요소의 태그, 속성, 자식을 변환한다
- **V2** 텍스트 노드를 변환한다
- **V3** 주석과 공백만 있는 텍스트를 구현이 정한 규칙대로 일관되게 처리한다
- **V4** 왕복: DOM → Virtual DOM → DOM 결과가 원본과 같다 (`canonical`로 비교)
- **V5** 빈 요소, boolean 속성(`disabled`), 깊은 중첩, 목록·표·폼
- **V6** 변환 함수가 입력을 바꾸지 않는다

### Diff + Patch (최소 변경 5가지 + 엣지)
- **D1** 노드 추가
- **D2** 노드 삭제
- **D3** 노드 종류 변경 (태그 변경, 텍스트 ↔ 요소) → 통째로 교체
- **D4** 속성 추가 · 변경 · 삭제 (동시에 일어나는 경우 포함)
- **D5** 텍스트 변경
- **D6** 바뀐 게 없으면 DOM 변경도 0
- **D7** 여러 자식을 한 번에 추가 · 삭제 (index가 밀리는 경우)
- **D8** 루트 교체, 없음 → 있음, 있음 → 없음
- **D9** 텍스트와 요소가 섞인 자식 (`가격: <b>100</b>원`)
- **D10** 연속 적용 (v0 → v1 → v2)

### History
- **H1** 저장, 뒤로가기, 앞으로가기
- **H2** 처음·끝에서 더 못 감
- **H3** 뒤로 간 상태에서 새로 저장하면 앞쪽 기록을 버린다
- **H4** (app) 이동하면 실제 영역과 테스트 영역이 함께 바뀐다

### 부분 업데이트 설계 확인 및 선택 확장
- **F1** 비교(diff) 단계는 DOM에 접근하지 않는다
- **F2** 비교·적용이 입력 Virtual DOM을 바꾸지 않는다
- **F3** 바뀌지 않은 DOM 노드는 같은 객체로 남는다
- **F4** 종류(type)가 다르면 해당 노드를 교체한다. key 변경 처리는 key를 구현한 경우에만 설계한 식별 규칙에 맞춰 확인한다
- **F5** 갱신 과정의 DOM 변경은 적용(patch) 단계에서 수행한다
- **F6** (key를 구현했다면) 순서만 바뀐 형제는 노드를 재사용해 옮긴다

이 항목은 부분 업데이트 설계 확인을 위한 기준이며 Fiber 자체의 구현을 요구하지 않는다. 비교 단계와 적용 단계가 한 함수에 섞여 있어 F1·F5를 검사할 수 없으면, 테스트하지 말고 보고에 "분리 안 됨"이라고 적는다. key 기능이 없으면 F4의 key 부분과 F6은 선택 기능 미구현으로 구분한다.

## 기법 (대상 개인의 `tests/helpers.js`)

**오라클 — 결과가 맞는지.** 이전 상태로 그린 화면에 변경을 적용한 결과가, 새 상태를 처음부터 그린 결과와 같아야 한다.

```js
assert.equal(canonical(patchedContainer), canonical(freshContainer));
```

**노드 재사용 — 최소 변경인지 (F3).** 적용 전 노드 참조를 잡아 두고 적용 후 `===`로 비교한다.

```js
const p = container.querySelector('p');
/* 텍스트만 바꾸는 변경 적용 */
assert.ok(container.querySelector('p') === p);
```

**DOM 변경 횟수 (D6).**

```js
const records = await recordMutations(container, () => /* 같은 상태로 적용 */);
assert.equal(records.length, 0);
```

**DOM 접근 감시 (F1).**

```js
assert.doesNotThrow(() => withoutDom(() => diff(oldV, newV)));
```

**불변성 (F2, V6).** 복사본을 얼려서 넘긴다. 수정하면 TypeError가 난다.

```js
const oldV = deepFreeze(structuredClone(v0));
assert.doesNotThrow(() => diff(oldV, deepFreeze(structuredClone(v1))));
```

**비교용 직렬화.** `innerHTML` 대신 `canonical(node)`를 쓴다. 속성 순서를 정렬하고 주석을 빼서, 올바른 구현이 순서 차이로 실패하지 않는다.

### 도구의 범위

- `canonical`은 주석을 제외한 요소·텍스트·DocumentFragment 구조를 비교한다. 폼의 현재 `value`·`checked` 프로퍼티, 이벤트 동작과 포커스는 별도로 검증한다.
- `parse`는 첫 노드만 반환하므로 여러 루트를 검사할 때는 직접 컨테이너를 만든다. 불변성 예제의 `structuredClone`은 복제 가능한 데이터에만 사용하며 함수·DOM 참조가 있는 VNode에 강요하지 않는다.
- `withoutDom`은 동기 실행 중 전역 `document`·`window` 접근을 감시한다. 미리 저장한 DOM 참조나 다른 브라우저 전역까지 차단하는 도구는 아니다.
- jsdom 검증은 실제 브라우저의 레이아웃·reflow·repaint와 사용성 검증을 대신하지 않는다. 화면 기능은 해당 개인의 앱을 브라우저에서도 확인한다.
